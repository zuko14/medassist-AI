Kriya AI Launch Gate

A source-of-truth audit of the MediAssist AI v2.0.0 repository against the claims in the existing forensic report. Every conclusion below is traced to a file, a migration, or an executed command. Where evidence is absent, it says so.

A. Executive verdict

Kriya AI is not ready for multi-tenant commercial launch, and it is closer than most systems at this stage. The transaction-critical layers are genuinely well built: slot uniqueness is enforced by a partial unique index that the application deliberately refuses to bypass, every payment status write is a compare-and-swap, the payment webhook refuses to guess a tenant, and the inbound message path is durable with a dead-letter queue and a reaper. Those are real engineering, and they hold up under reading.

What does not hold up is the layer beneath them and the evidence on top of them. The database cannot enforce the platform's most basic invariant, because clinic_id is nullable on all nine core tenant tables — the SET NOT NULL statements were written and then commented out, and never applied since. A row that loses its tenant is then resolved by a helper that silently returns the oldest active clinic, which is how a report or reminder would be sent through another hospital's WhatsApp number. Separately, the test suite is not hermetic: settings load the repository's .env at import time, three production clinic identifiers are hard-coded into assertions, and a run with the database unreachable produces 16 failures. The "438 passed, 0 failed" figure in the prior report was obtained against the production database and cannot be reproduced in continuous integration.

The right next step is a supervised single-tenant or two-tenant pilot while Phase 0 and Phase 1 are executed. Opening the platform to many tenants before the schema enforces tenancy is taking a risk the code cannot see.

D

Critical findings

No P0 was confirmed. The classic P0 candidates — concurrent double booking, cross-tenant payment confirmation, duplicate message processing, authentication bypass — were each traced to a working control. The five P1 findings below are what stand between this system and a defensible multi-tenant launch.

P1KA-A-01Database · Multi-tenancy

The tenant key is nullable on every core table, so the database cannot enforce tenancy

Location
migrations/004_seed_first_clinic.sql:37–46 — all nine ALTER … SET NOT NULL lines are commented out. No later migration applies them; a repository-wide search for SET NOT NULL returns only those comments.
Affects
patients, appointments, conversations, lab_reports, prescriptions, analytics_events, doctors, doctor_leaves, hospital_holidays.
Failure
Any insert path that omits the tenant key produces a row belonging to no clinic. Every row-level security policy is written as clinic_id IS NOT NULL AND clinic_id = …, so such a row is invisible to every tenant under those policies while remaining fully visible to the application, which connects with the bypassing service role. The strong application-layer guards therefore rest on a schema that permits exactly the state they are designed to prevent.
Why tests miss it
Every test constructs rows with a clinic identifier, so no test observes the column's nullability. The real-PostgreSQL suite asserts on indexes and constraints but never on column nullability.
Fix
A migration that reports orphans, quarantines or backfills them, then applies SET NOT NULL to all nine columns. Pair it with a check constraint forbidding the literal string default wherever the column is text.
P1KA-A-02Multi-tenancy

A missing tenant identifier silently resolves to the oldest active clinic

Location
app/services/tenant.py:256–270 — get_clinic_by_id treats None, an empty string, "default", "none" and "null" as a request for the first active clinic ordered by creation date.
Callers
Roughly a dozen sites pass a row's own key straight through, written as get_clinic_by_id(row.get("clinic_id", "default")): scheduler.py:519, 718, 887 · lab_reports.py:836, 1051 · payment.py:767, 1630 · prescriptions.py:156.
Failure
Chained with KA-A-01: a prescription, appointment or lab report whose tenant key is null is attributed to a different hospital. The clinic object returned carries that hospital's Meta access token, phone number identifier and display name, so the outbound reminder or report is sent from the wrong hospital's WhatsApp number, to a patient who never contacted it. This is a cross-tenant disclosure with no log line that names it as one.
Census
Latent, not live. The 2026-09-09 census found zero null-tenant rows across all nine core tables, so no row currently takes this path. The severity stays P1 because nothing prevents the state — the guard is absent, not merely unused.
Why tests miss it
The sentinel path is only reachable when a row is already malformed, and no test constructs a null-tenant row — the schema is what would have made that impossible.
Fix
Make the sentinel branch raise TenantNotFound. Where a genuine bootstrap needs the sole clinic, add an explicit get_primary_clinic() that refuses when more than one active clinic exists, mirroring the rule already applied in tenant resolution and in the payment webhook.
P2KA-A-17Payment ledger

Fourteen payment-event write paths omit the tenant key, including every refund and admin action

P1KA-A-03Test integrity

The test suite runs against the production database, and its green result is not reproducible

Location
app/config.py:214 loads .env and instantiates settings at import time, which happens during collection — before the session-scoped fixture in tests/conftest.py can set its defaults. The repository's .env holds live Supabase credentials. tests/test_patient_metrics_production.py:8–10 hard-codes three production clinic identifiers and asserts on their live row counts.
Observed
Executed with the database made unreachable: 1785 passed, 16 failed, 2 skipped in 196 seconds. Three failures are network errors on staff routes; the rest are assertion failures spanning conversation dispatch, scheduler reminders, health check-ins, report dispatch gating and dashboard patient metrics.
Impact
Three separate problems. The prior report's "438 passed, 0 failed" was produced against production and is not evidence a reviewer can re-derive. The continuous-integration workflow supplies dummy credentials, so it cannot be green on the same tests. And a routine test run reaches production with a service-role key, which is the documented mechanism behind the scheduler-lock incident that starved the live connector.
Fix
Make settings lazy, or force the test environment before import through a root-level conftest. Replace hard-coded production identifiers with fixtures. Add a guard that aborts collection if the resolved database host is not a test host.
P1KA-A-04Admin correctness

Dashboard reads truncate at 2,000 rows and then filter in Python, silently

Location
app/routers/admin.py:930, 1570, 1581, 2050, 2563, 2726, 3314, 3858, 4458, 4832–4846 · 4960 (5,000) · app/database.py:379–429.
Failure
The report delivery log fetches the newest 2,000 rows and then applies the day-window filter in Python. A clinic past 2,000 lifetime reports sees a window that quietly excludes anything the cap cut off, and the counts derived from it are wrong rather than merely partial. No response carries a truncation flag, so neither the operator nor the front end can tell. The same shape appears in patients, doctors, leaves, holidays, staff and connector failure lists.
Business impact
Revenue, appointment and report figures shown to a hospital become understated as it grows, with no visible symptom. That is the failure mode a dashboard must never have.
Fix
Push date and status filters into the query, return keyset pagination with a cursor, and have every capped response carry an explicit truncation flag the panel renders.
P1KA-A-05Admin security

The platform owner console is protected by HTTP Basic alone

Location
app/routers/platform.py:43–90 — verify_owner_credentials, applied to every one of the console's 30-plus endpoints.
Failure
This is the highest-privilege surface in the system: cross-hospital revenue, patient activity, clinic provisioning, connector configuration and admin password resets. It has no session, no server-side revocation, no multi-factor step and no per-account lockout. The password comes from an environment variable and may be stored in plain text — the hashed branch is optional and chosen by prefix. Credentials travel on every request and sit in the browser's credential cache. By contrast the clinic console, which is strictly less privileged, already has revocable sessions and an audit log.
Also
Brute-force accounting is keyed on client address and shares one global limiter with the clinic login, so attempts against either surface consume the other's budget from the same address.
Fix
Give the platform console the same session mechanism the clinic console already has, add a time-based one-time-password step, add per-account lockout distinct from per-address throttling, and require a hashed password rather than accepting plaintext.

Security and multi-tenant findings

P2KA-A-12Operational safety

Two tracked scripts delete every patient and conversation across all tenants

Location
reset_db.py · temp_reset.py — both import the service-role client and issue an unfiltered delete on conversations and patients.
Failure
They are not copied into the container image, so production cannot run them. They are in the repository and they read .env, so any developer machine holding production credentials is one command away from wiping every tenant's patients. There is no confirmation prompt and no environment check.
Fix
Delete both. If a reset utility is genuinely needed, put it under scripts/, require an explicit clinic identifier, and refuse to run when the resolved environment is production.
P3KA-A-16Auth hardening

No multi-factor step, no account lockout, and Basic auth retained beside sessions

Location
app/routers/admin.py:396–435 and 200–290.
Failure
Brute-force accounting is per source address at five attempts a minute, with no per-username counter, so a distributed attempt against one known administrator is unthrottled. There is no lockout and no notification on repeated failure. The Basic fallback is retained for scripts, which keeps cached browser credentials available to any cross-site form post that a JSON endpoint happens to accept.
Mitigating
The session cookie is HttpOnly, strictly same-site and secure in production, and only its hash is stored. Sessions are revocable and every admin action is written to an audit log.
Fix
Add per-username attempt accounting and lockout with an operator unlock path. Scope the Basic fallback to a header-only interface, or retire it once the panel no longer needs it.
Not found: no committed secrets — a scan for provider key shapes across every tracked file returned nothing, and .env is correctly ignored. No SQL string interpolation: all database access goes through the query builder. The security header set, including a restrictive content security policy, is applied to every response.
G–H

Booking, concurrency and payment findings

This is the strongest area of the system, and the two findings here are about capacity and coverage rather than correctness. The core invariant — one physician, one clinic, one minute, at most one active appointment — is enforced in the database, tested against real PostgreSQL under 50-way contention, and the application refuses to write rows the index could not guard.

P2KA-A-09Payment · Capacity

The hold-expiry sweep can outlive its own lease

Location
app/services/payment.py:905–1040, registered with a 60-second lease on a one-minute interval.
Failure
The sweep selects up to 200 stale holds and, for each one that carries a payment link, makes a sequential call to Razorpay before deciding whether to expire it. At a few hundred milliseconds per call the job exceeds its lease, the heartbeat detects the loss and cancels the body, and the tail of the batch is never processed. Those slots stay held and unsellable until a later tick happens to reach them.
Also
The 200-row cap sets the ceiling on how fast held slots return to inventory. A clinic generating more than 200 expiries a minute accumulates a permanent backlog.
Fix
Bound the batch by remaining lease time rather than row count, issue the provider checks concurrently under a semaphore, and raise the lease to match the worst-case batch. Emit a counter for unprocessed remainder so the backlog is visible.
P2KA-A-10Booking logic

Lab-test bookings have no uniqueness and no capacity limit

Location
migrations/064 — both uniqueness indexes are predicated on consultation bookings; app/database.py:995–1000 skips the pre-check for lab rows.
Failure
This is deliberate and documented: a lab test reserves a collection day, not a minute, so slot uniqueness would be the wrong constraint. But nothing replaces it. No per-day, per-branch collection capacity is enforced anywhere, so an unbounded number of patients can be confirmed for the same collection day at the same centre, and the centre discovers the overbooking when they arrive.
Fix
Add a configurable daily collection capacity per branch, checked in the booking transaction and backed by a counter the database maintains, not by a read-then-write in application code.
I–J

WhatsApp and connector findings

P2KA-A-08WhatsApp reliability

The per-patient lock fails open, so two messages can interleave across processes

Location
app/services/message_queue.py:766–782 — a failure to acquire the database lease is caught and processing continues with only the process-local lock.
Failure
The comment justifies this by pointing at the message-identifier uniqueness guard, but that guard prevents the same message being processed twice; it does nothing about two different messages from the same patient landing on two different workers. With four web processes, a database blip during a burst lets both run the conversation handler concurrently and interleave writes to the same conversation state, which is precisely the corruption the lock exists to prevent.
Reproduce
Make the lock call fail, then deliver two distinct messages for one phone number to two workers within the same second, and observe the resulting state and context.
Fix
Fail closed and defer to the retry queue, which already exists and already handles the 15-second timeout case. Emit a counter so the degraded window is visible rather than inferred.
P2KA-A-07Connector reliability

Report delivery is at-least-once, and its idempotency pre-check fails open

Location
app/routers/integrations.py:141–200 for the pre-check, 306–360 for the dedup insert after delivery · connectors/runner.py:944–961 repeats the same ordering.
Failure
The processed-report row is written after the send has already delivered the report on WhatsApp, and a failure of that write is logged and swallowed. Worse, the pre-check itself is wrapped in a handler that logs "idempotency check failed (proceeding)" — so a database blip during a connector poll does not skip the batch, it re-delivers every report in it to patients who already received them.
Guarantee
The honest classification is at-least-once. A secondary cross-path check against the report table narrows the window but is subject to the same fail-open handler.
Fix
Claim the external report identifier before delivery by inserting a row in a claimed state and promoting it afterwards, so a crash leaves a claim rather than a gap. Make the pre-check fail closed and defer the batch.
P2KA-A-11Patient safety

Wrong-patient delivery is not structurally prevented for diagnostic centres

Location
app/services/patient_match.py:113–145 — the hold decision returns false for clinics typed as diagnostic or flagged for walk-in delivery.
Failure
For those tenants a report clears delivery with no corroboration from Kriya's own patient registry, so the recipient is whatever phone number the external system holds. A transposed digit at the reception desk sends a stranger's laboratory results to an uninvolved person. The only control is an advisory flag on the delivery and an administrator notification raised after the message has gone.
Assessment
The reasoning is sound — a walk-in centre has no registry to check against, and holding every report would block the whole pipeline. But the invariant "a patient's report is never delivered to another patient" is delegated to the third-party system, and that should be stated in the contract rather than implied by the architecture diagram.
Fix
Where the source supplies one, verify a second identifier — date of birth or a report reference — before automated send. Otherwise make the unverified state explicit to the clinic and require an operator to release the first delivery to any phone number the tenant has not seen before.
K–L

Database and front-end wiring findings

Beyond KA-A-01, the schema is in good shape. Seventy-three ordered migrations are checksummed and tracked; the destructive ones carry pre-flight reports that name the rows they will quarantine before they change anything; and the slot re-keying migration in particular reads as work done by someone who had already been burned once. Three tables have down-migrations, which is the main gap.

Two unbounded tables need an archival policy before they become a problem: the outbound message ledger writes one row per Meta API call with the recipient's phone number and has no purge job at all, and the connector audit log grows one row per poll per connector per minute.

Front-end wiring was checked by extracting every request the admin panel makes and matching it against the router. All 58 call sites resolve to real endpoints with matching methods, the shared helper appends the tenant scope to every path so the panel cannot accidentally issue an unscoped call, and the failure handler distinguishes an expired session from a tenant-boundary rejection — including the case where a second browser tab has re-authenticated as a different user, which it detects and stops rather than continuing to fire cross-tenant requests. That is unusually careful. The gap is the same one as KA-A-04: no endpoint returns pagination metadata, so the panel cannot show that a list was truncated.

M–N

Admin, platform and scalability findings

Role separation is real: staff accounts are gated out of finance, roster and integration actions, permissions are checked server-side per route rather than by hiding controls, branch scope is enforced separately from clinic scope, and every mutation is written to an audit log. The weaknesses are KA-A-05 above and the query shapes below.

P3KA-A-13Scheduler

One scheduler job runs without a distributed lease

Location
app/services/scheduler.py:1219 — the message-queue fail-open alert, registered on a ten-minute interval, is the only job body with no distributed lock.
Failure
Every process runs it, so a genuine queue degradation raises one alert per process. Alert duplication trains operators to ignore the channel, which is how the next real alert gets missed.
Fix
Wrap it like the other 22 jobs.

Scalability. The binding constraints are structural rather than tuning. Per-process database concurrency is capped at 16 worker threads, deliberately reduced from 64 after a cascading-timeout incident, and the comment is explicit that raising it again is unverified. Above that sit the 2,000-row query caps with client-side filtering, sequential external API calls inside scheduler sweeps, and two tables with no archival. There is no partitioning anywhere. None of this is wrong for a handful of tenants; all of it becomes the first thing to break at a hundred.

O–P

Reliability and silent-failure findings

A scan of the application and connector packages found no bare except clauses, and roughly 50 broad exception handlers that end in a pass or an equivalent. Most are deliberate and carry a comment explaining the choice. Three fail-open handlers are load-bearing enough to matter, and all three are already recorded above: the connector idempotency pre-check, the per-phone distributed lock, and the prescription reminder dedup insert, whose failure is logged and lets the reminder resend on the next five-minute tick.

The general pattern is good. Failures that would lose a patient message raise rather than return; the webhook re-raises after logging so the dead-letter path can see it; and the codebase distinguishes a transient database error from a permanent tenant-resolution failure and routes them to different retry budgets. The place the pattern breaks is the erasure path, which is section S.

Failure injection has not been exercised against the deployed system. Every claim about behaviour during a database outage, a Meta timeout or a container restart is derived from reading the handlers, not from watching them run.

Q–R

Observability and AI safety findings

Observability. Sixteen named counters cover the failure modes that matter — dead letters, fail-open windows, lock theft, unmatched payments, slot contention, refund failures, reaped claims, unreconstructable recoveries. Correlation identifiers are threaded through requests and returned on the response. The metrics endpoint is authenticated. Phone numbers are masked in logs at every site checked. What is missing is everything downstream: no dashboard definitions, no alert routing, and no service-level objectives are present in the repository, so whether anyone is actually paged when the dead-letter counter climbs is unknown. The alerting that does exist sends WhatsApp messages to an administrator, which is a notification channel, not a monitoring system.

AI safety. This is the cleanest area in the audit. The model is never authoritative: a deterministic clinical firewall intercepts medication, dosage and diagnosis requests before any model call, so the model is not even consulted on the questions that carry medical liability. Intent classification output is validated against a fixed whitelist and falls back to keywords on anything unexpected, on malformed output, and on provider failure. Prompt-injection detection routes straight to the deterministic path rather than to a sanitised prompt. Nothing in the model's output reaches a booking, a payment amount, a tenant selection or an authorisation decision.

S–T

Privacy and deployment findings

P2KA-A-06Privacy · Data lifecycle

Erasure leaves named copies of the patient's phone number, and reports success regardless

Location
app/services/data_retention.py:174–380 · app/database.py:1179–1220.
What works
The tiered design is sound and unusually complete for its stage: clinical rows are anonymised rather than deleted to satisfy medical retention, conversations and analytics are deleted outright, stored report files are removed from object storage before the row is redacted, the durable inbound queue is pseudonymised while keeping the message identifier as an anti-replay tombstone, and the whole operation is written to an audit log.
What remains
Four named copies survive. The patient row keeps its phone number — only the name and consent flags are cleared, and the phone number is the identifier. The outbound message ledger stores the recipient phone as a non-null column, is never touched by erasure, and has no purge job of any kind. The failed-message queue retains the phone and the message payload, purged on a 30-day timer but not on request. And the admin audit log's detail payloads are not reviewed for patient content.
Worse
The deletion entry point returns success whenever no exception escapes, without inspecting the per-table error list the anonymisation function carefully collects. A patient can be told their data is gone while the lab-report redaction silently failed.
Fix
Redact or hash the patient phone; pseudonymise the outbound ledger and give it a retention job; include the failed-message queue in erasure; propagate the error list and return failure so the patient is told the truth and an operator is alerted.

Deployment. The image is sound: non-root user, tini as process 1 to reap browser zombies, the timezone pinned to the one every naive datetime in the codebase assumes, the browser path fixed so the runtime user finds what the build user installed, health and readiness probes wired, migrations run as a pre-deploy step, and a bounded drain of in-flight background work on shutdown. Both main-branch services auto-deploy together so the web service and the connector worker cannot sit on different commits.

Two things need attention. Test tooling ships in the production image because pytest and its asyncio plugin are in the runtime requirements file. And the audit could not confirm that the declared topology matches the provisioned tier — the concurrency reasoning throughout the code is written for four web processes, and if the live tier runs one, several of the distributed-correctness arguments are being tested for the first time on the day it scales.

V

Capacity model

The existing load-test report states a 95th-percentile latency of 0.17 milliseconds for 200 concurrent webhook requests. That figure is not a load test. Its own header names the harness as a pytest file, and sub-millisecond latency is only achievable in-process with the transport mocked. A Locust file exists and is well written, but no results from it are recorded anywhere in the repository. Deployed capacity is unmeasured.

What can be derived from the code is a ceiling, not a throughput. Per-process database concurrency is capped at 16 worker threads. At the declared four web processes that is 32 concurrent database calls platform-wide. A single booking turn makes roughly 15 sequential database round-trips plus one model call, so at 50 milliseconds per round-trip a turn occupies a thread for close to a second.
